# Zoer Connect 0.3.14 qualification

- New connection keys enable Push and prepare shared-hosting migration in the same authenticated administrator POST. Pull remains opt-in. Site publication still requires the existing per-transfer replacement confirmation in Zoer.
- Key reset preserves existing permission choices. Revoked permissions stay disabled when generating a replacement key. Page views and plugin updates do not enable disabled access or rewrite existing setup.
- Automatic preparation validates private storage and hosting compatibility, installs the existing MU protection, and records a destination-bound version 4 readiness receipt. It does not claim that a content replacement was accepted or that PHP workers were isolated. Version 2 verified-worker and version 3 shared-hosting receipts remain supported.
- Existing advanced, stale or incomplete setup remains intact. Active recovery blocks setup changes. Preparation failures leave the connection key available and explain the required administrator action.
- `make test` passed under unprivileged Linux PHP 8.1, 8.2 and 8.3 containers, including new connection-form/default-setup coverage and the existing publication, rollback, request-drain and updater suites. The local macOS run passed the new checks but cannot complete Linux worker verification; the Linux runs provide that coverage.
- Expect browser checks against the actual form renderers in a local WordPress boundary fixture passed: first key generation, Push on/Pull off, shared readiness, saving disabled Push and enabled Pull, reset preservation, revocation/regeneration, hiding the secret on GET, and repeated reset at phone width. No script errors were captured. This is form coverage, not a live WordPress browser or Zoer publishing workflow test.
- A new disposable WordPress 7.1.2 / MariaDB 11.4 installation passed `tests/integration/connection-defaults.php`: real WordPress option persistence, form processing, automatic readiness, REST status dispatch reporting a publish-ready destination, permission/reset/revocation behavior, and stale-destination refusal. No production site was contacted or changed.
- `make test-package` passed deterministic ZIP and layout checks. The resulting ZIP was installed into the disposable WordPress instance; key settings and private readiness remained byte-equivalent across installation, and the installed plugin reported 0.3.14.
- The package checksum and exact runtime file hashes are recorded in `0.3.14.json`. Existing live sites need the plugin update; updating does not automatically change their saved permissions or publish site content.
