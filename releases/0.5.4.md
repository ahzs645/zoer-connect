# Zoer Connect 0.5.4 (development)

## Request-protection MU file survives copies and plugin removal

Setting up request protection installs `wp-content/mu-plugins/000-zoer-connect-fence.php`,
which WordPress loads on every request. Through 0.5.3 it required Zoer Connect's
files by this installation's absolute path without checking them, so:

- a copy of the site made by anything other than Zoer (a hosting backup restored
  elsewhere, a manual file copy, another migration tool) failed with a fatal error on
  every request, including wp-admin;
- removing or renaming the `zoer-connect` plugin folder took the site down the same way.

The 0.5.4 bootstrap does nothing when `ABSPATH` is not the installation it was written
for, and does nothing when Zoer Connect's files are missing while no transfer holds the
fence. If a transfer is paused and the plugin files are gone, it answers 503 with
guidance to reinstall Zoer Connect and finish or roll back the transfer, instead of
running ordinary plugin code or failing fatally.

Existing 0.5.x MU files still verify after the update, so upgraded sites keep serving
requests. When an administrator next opens wp-admin, a 0.5.x file is replaced with the
new form in the same cache mode; this never happens while a transfer holds the fence.
Setup replaces either form. Because the request-fence code changed, its readiness
receipt no longer matches: confirm destination setup again under Tools > Zoer Connect
before the next import into the site.

`tests/write-fence.php` runs the generated MU file in fresh PHP processes for a copy
at another path, a removed plugin with and without a paused transfer, a 0.5.x file
after the update, its replacement in both cache modes and its refusal during a
transfer. With the 0.5.3 bootstrap the copy and removal cases reproduce the reported
`require_once(...WriteFence.php): Failed to open stream` fatal.

This is development source; no tag, update feed or hosting qualification is provided.
