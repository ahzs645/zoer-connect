# Zoer Connect 0.4.0 — UNQUALIFIED prerelease

Prerelease notes, last updated 2026-10-02. The `v0.4.0-rc.1` prerelease is for disposable-site testing only and does not update the public WordPress feed. There is no qualification receipt (`releases/0.4.0.json`), so `scripts/check-release.py` fails and the CI `package` job stays red on every branch push; that is expected. Do not tag `v0.4.0`, publish it to the public update feed (`ahzs645/zoer-connect-releases`) or install it on a production site until the checklist below is complete and recorded. Local ZIPs from `make build` are for disposable test sites only.

0.4.0 is API version 2: WP Migrate-style transfer options and batched Push uploads. Every addition is optional; a client that sends none of them gets 0.3.14 behaviour. `WriteFence.php`, `RequestDrain.php` and the MU bootstrap are unchanged, so updating does not invalidate existing import readiness. The matching Zoer backend (WordPress Manager on the `feature/zoer-connect-parity` branch) sends an option only when this plugin advertises its capability. The README section "API version 2 (0.4.0)" is the protocol reference.

## Changes

### Status and diagnostics

- `/status` reports `apiVersion: 2`, `version: "0.4.0"`, 17 feature capability flags, `batchUpload`, `batchDeflate`, `batchTransports` and `batchLimits`.
- `GET /diagnostics` for Push or Pull keys: read-only WordPress, PHP and database facts (tables with engine, rows, bytes, primary/foreign keys, triggers), post types, themes, plugins, MU plugins and drop-ins, the pending plugin update, and warnings (`firewall_plugin`, `page_cache_plugin`, `object_cache_dropin`, `mixed_case_tables`, `non_innodb`, `foreign_keys`, `triggers`, `blog_private`, `no_https`).

### Pull

- `database` filter object: table suffix subset, post type inclusion list, exclude revisions, exclude spam comments, transients excluded by default. Dependent postmeta, comments, commentmeta and term relationships follow excluded parents inside the same consistent snapshot. `database: true` keeps the 0.3.14 query byte for byte; with a filter object the transient patterns escape LIKE wildcards.
- Profile modes: `themesMode`/`pluginsMode` (`all`, `active`, `selected`, `except`) with item slugs, and `mediaSince` (UTC date). Export `source` reports `abspath` and exported `tables`.
- Fix: snapshots no longer fail with "Schema changed during export." when a concurrent insert (a transient written by a page view, a cron lock) advances a table's `AUTO_INCREMENT`; MySQL 8 and MariaDB report the live counter even inside the consistent snapshot. Reproduced in 10 of 20 runs under insert load on MySQL 8.0, 0 of 20 with the fix.

### Import (Push)

- Optional `sourcePath` and `options`: `replacements` (`automatic`, `variants`, `paths`, up to 50 `custom` literal or regex rows), `replaceGuids`, `keepActivePlugins`, `keepActiveTheme`, `authorMapping` (`administrator` or `match`), `createTables`, `partialDatabase`, `fence` (`early` or `activation`), `review` and `purgeCaches`.
- Without `options`, the 0.3.14 sequential replacement rules apply byte for byte. With options, generated rules run as one longest-match pass, and original URLs under the source home map to the destination siteurl.
- Replacement engine: the value limit is 16 MiB (was 1 MiB) and applies only to values a rule can match; case-insensitive literals; per-table counts and up to 20 before/after samples.
- New phases `mapping_authors`, `review_required` and (replace kind) `snapshotting`; with the activation fence, tables are staged while the site stays live and the site pauses only from the fenced check in `reserving`. A live change detected before or under the fence cancels the import with a safe error and never leaves the site paused. Live cron and maintenance options are copied into the stage under the fence just before the swap.
- Actions: `/pause`, `/resume`, `/approve`, `/cleanup`, and `GET /imports` (newest 50).
- `kind: "replace"`: find-and-replace on the destination's own database. It fingerprints the selected tables, then snapshots only those tables (keeping other tools' options such as `wpmdb*` settings, which Pull still omits), and continues through review and the activation fence.
- `createTables`: strict single-statement `CREATE TABLE` validation (InnoDB, primary key, no foreign keys, partitions, data directories, comments, backslashes, generated columns or other statements); created tables roll back by rename and are dropped on cleanup. Table creation and replace jobs refuse tables of another WordPress installation whose prefix extends this site's.
- Safe errors: `{code: "zoer_import_failed", message, phase}` with plugin-authored text only, paths redacted, at most 300 characters; persisted as the import's `error`.
- `purgeCaches`: on the next normal `wp_loaded` after finish or rollback, calls LiteSpeed, WP Rocket, W3 Total Cache, WP Super Cache, Breeze, WP Fastest Cache, Cache Enabler, SG Optimizer and Autoptimize purge hooks and `wp_cache_flush()`.
- Fix: rolling back a file publication also removes the directories that publication created (when empty), so rolling back a new theme or plugin no longer leaves an empty folder that WordPress lists as a broken theme.

### Batched upload

- `POST /imports/{id}/batch`: ordered spans of 256 KiB blocks, each checked against its manifest SHA-256 before it is written. Transports: `ZBT1` framed `application/octet-stream` (optionally one zlib stream per span, inflation bounded to the declared size), a multipart file part `batch`, or JSON with base64 spans. Idempotent skip, torn-tail repair, `gap`/`bounds`/`unverifiable`/`decode` rejections, about 2 s of work per request, and 413 `zoer_import_body_limit` with the current limits.
- Limits: `maxBatchBytes` = min(`post_max_size` − 64 KiB, 8 MiB) (multipart also within `upload_max_filesize`; filter `zoer_connect_max_batch_bytes`), 1,024 spans, 2 MiB JSON.
- Fixed-width `artifacts.idx`/`blocks.idx` and an atomic `upload.json` cursor, written at create and built lazily for older journals; `GET /imports/{id}?view=upload` returns the cursor without the import lock.
- `/chunks` responses and messages are unchanged and share the block writer, so a job can switch transports mid-upload.

### Administration

- Tools → Zoer Connect → Transfers: recent imports with **Clean up backups** for finished imports, including journals created before a key rotation. Export profiles are editable with the theme/plugin modes and media date.

## Local evidence (not a qualification receipt)

All runs on 2026-09-29, local machine, plugin from the working tree.

- **Unit suites:** `make test` passes under PHP 8.1 and PHP 8.3 (Docker PHP containers). CI additionally runs PHP 8.2.
- **Docker end-to-end** (`tests/e2e-docker/run.sh`): WordPress 7.1.2, PHP 8.3.35 (Apache), HTTPS through Caddy `tls internal`. 225 checks, 0 failed, on MariaDB 11.4.13 and on MySQL 8.0.46 (runs after the `AUTO_INCREMENT` fix). Coverage: status and diagnostics, filtered paged Pull, Push with every import option, review/approve, late fence, rollback refusal and success, cleanup, a legacy client, `kind: "replace"`, late-fence abort, pause/resume, list, safe errors and batched upload (scenarios 1–9 in `tests/e2e-docker/README.md`). A separate loop of 60 replace imports with deliberate front-page and `wp-cron.php` traffic showed no lost or invented option writes; the earlier intermittent failures were WordPress's own `wp_update_comment_type_batch` cron job, which the fixture now makes deterministic with `DISABLE_WP_CRON`.
- **Batched push (scenario 9):** the same export of 243 artifacts (about 8.7 MB) needs 243 `/chunks` requests and 6 `/batch` requests (octet-stream 2, octet-stream + deflate 1, JSON 1, JSON + deflate 1, multipart 1, plus 1 idempotent retry), and publishes exactly what the `/chunks` push published.
- **Zoer backend interop** (`backend/scripts/zoer-connect-batch-interop.ts` in the Zoer repository, the production uploader and connector sender against this fixture; 243 artifacts, 8,745,132 bytes):
  - baseline: 4 `/batch` requests, octet-stream with deflate (8,214,709 bytes on the wire), adaptive growth to the advertised 8,323,072-byte limit;
  - body-limit learning: after `post_max_size` was lowered to 1M mid-upload, the plugin answered four 413 `zoer_import_body_limit` responses, the client learned a 927,314-byte ceiling without backoff or a transport change, and finished in 10 accepted requests;
  - transport fallback: one 415 for octet-stream, then 6 multipart requests; 415 for octet-stream and multipart, then 7 JSON requests.
  Every run completed review, approval, finish, verified the published data, rolled back and cleaned up.

None of this covers certificate trust, public proxies or CDNs, real hosting limits, large transfers, process kills or the Zoer interface.

## Qualification required before a receipt or tag

- [ ] Real Zoer UI against disposable DDEV (or disposable cluster) WordPress sites only, never SparkLab or another production site: Pull, Backup, Export and downloads; Push from a local DDEV export and from a verified Pull of another site (remote → remote); Find & Replace with review; pause/resume, approve, finish, rollback and cleanup; local copy refresh; desktop and 390 px widths.
- [ ] Public proxy and TLS: real certificates and hostname verification through Zoer's pinned HTTPS requester, a real reverse proxy (Traefik/nginx, Cloudflare where used) and connector-route passthrough.
- [ ] Page caches and CDN: connector routes excluded from caching; `purgeCaches` against installed LiteSpeed, WP Rocket or Breeze; confirm what a host or CDN cache still serves.
- [ ] Real shared hosting limits: `post_max_size`, `upload_max_filesize`, `max_execution_time`, `open_basedir`, disabled functions (including zlib `inflate_*`), PHP-FPM pools, and web application firewalls (ModSecurity or host rules) that refuse `application/octet-stream` or multipart bodies. Confirm 413 learning and transport fallback on a real host.
- [ ] Very large transfers: multi-GiB database and file sets, files near 2 GiB, and hosted remote Pull near its 256 MiB / 40 s snapshot bound.
- [ ] Process kills at journal boundaries: PHP worker death during a batch append, index/`upload.json` writes, table staging, activation, cleanup and rollback, then recovery through the same connection.
- [ ] Advanced verified-workers mode with API version 2 options (activation fence, review, replace kind).
- [ ] Mixed versions: an older Zoer client (0.3.x backend, `/chunks` only, no options) against 0.4.0, and the new Zoer backend against a 0.3.14 destination (capability gating, `/chunks` fallback, refusal of non-default options).
- [ ] Database coverage beyond the fixture: MariaDB 10.x, `lower_case_table_names` other than the image default, mixed-case prefixes.
- [ ] `update_plugins` transient and `pluginUpdate.latest` against the real public feed on an installed site.

## Release steps (after qualification)

1. Record the evidence in the Zoer repository's `output/ui-audit/` and summarize it here, replacing the UNQUALIFIED heading.
2. Finalize `readme.txt` first: it is a packaged runtime file hashed by the receipt.
3. Run `make test`, `make test-package` and `make build`; write `releases/0.4.0.json` with `qualified: true`, the runtime file hashes and the ZIP SHA-256; confirm `python3 scripts/check-release.py --package` passes.
4. Commit, push an annotated `v0.4.0` tag, and let the workflow publish the private release and the public update feed.
