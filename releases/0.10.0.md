# Zoer Connect 0.10.0

Connection keys gain a separate **Code** permission for plugin and theme files, update manifests
can be Ed25519-signed, and the import routes' REST fallback authenticates in its permission callback.

## Connection key scopes

- New keys start with **Push**, **Pull** and **Code** off. The key form offers Push and Code
  checkboxes, both unchecked; the Code choice warns that it lets the key holder install PHP that
  WordPress runs. Choosing Push still prepares shared-hosting migration in the same request.
- **Push** stages and imports media uploads (`wp-content/uploads`, where executable files were
  already refused) and the database. **Code** is required in addition to Push for any transfer that
  writes `wp-content/plugins/` or `wp-content/themes/`, or that replaces the destination's plugin or
  theme selection (`resources.plugins` / `resources.themes`). Code without Push grants nothing.
- Enforcement: import creation (`POST /imports`), legacy staging (`POST /jobs`), and `step`,
  `approve` and `resume` of an import whose journal carries plugin or theme files. Turning Code off
  therefore stops such an import before (more of) it is applied; `status`, `pause`, `finish`,
  `rollback` and `cleanup` stay available so it can always be recovered. Uploads only reach private
  staging and are not re-checked per block (that would decode the journal on every batch).
- Application-password administrators are not limited by key scopes: they can already install
  plugins through WordPress.
- **Existing keys.** A key stored before 0.10.0 has no `code` field. If it has Push it keeps code
  access, so the owner's current pairing keeps working. Tools → Zoer Connect → Permissions flags it
  as a legacy key and shows Code as on; saving permissions records an explicit choice. Resetting
  the secret key keeps Push and Pull but asks for Code again (unchecked unless the stored choice was
  an explicit yes), so legacy code access is never carried forward silently. Revocation turns Code
  off.
- `GET /status` reports `permissions.code`, `permissions.legacyCode` and the `codeScope`
  capability, so Zoer can explain a refusal before it uploads.

## Signed updates

- `update.json` may carry `signature`: a base64 Ed25519 detached signature over
  `"zoer-connect-update-v1\n" + version + "\n" + sha256 + "\n"`, verified with
  `sodium_crypto_sign_verify_detached` (WordPress ships sodium_compat).
- The verifying key is `GitHubUpdater::PUBLIC_KEY` (empty in this version: no signing key has been
  provisioned) or `ZOER_CONNECT_UPDATE_PUBLIC_KEY` defined in `wp-config.php` (base64 of the 32-byte
  public key). With a key, unsigned or badly signed manifests offer no update and their downloads are
  refused; the unsigned legacy bridge feed is refused too. A configured key that is not a valid
  32-byte key (or a PHP without sodium) refuses every update and shows an error notice.
- Without a key, behaviour is unchanged (SHA-256 from the same release) and administrators who can
  update plugins see a warning on Plugins, Updates and Tools → Zoer Connect that updates are unsigned.
- `scripts/build-update-manifest.py` signs when `ZOER_CONNECT_UPDATE_SIGNING_KEY` (base64 64-byte
  libsodium secret key or 32-byte seed) is set, through `scripts/sign-update.php`. When the plugin
  ships a public key, signing is mandatory and the signing key must match it. CI passes the
  `ZOER_CONNECT_UPDATE_SIGNING_KEY` repository secret to the manifest steps.
- Fix: `download()` accepted a release-candidate manifest on every site. Only sites on the
  release-candidate channel accept one now; the stable channel refuses a candidate's ZIP.

## Import route authentication

The REST registration of `/imports…` (the fallback used when the MU request fence is not
installed) used `__return_true` and authenticated inside its callback. Its permission callback now
runs the same uncached key, scope and owner checks (`Plugin::recoveryAuth`) that the MU fence
handler uses before regular plugins load; the handler still re-checks them.

## Verification

- `make test` (PHP 8.3, run as a non-root user) and `make test-package` pass locally. New tests cover
  key defaults, the Code scope on staging, import creation and import steps, legacy keys, the admin
  form, the import routes' permission callback, signature verification (unsigned, malformed,
  foreign-key, wrong-checksum and wrong-version signatures, unusable keys) and signed manifests.
- Release check (2026-11-01): `make test` on PHP 8.3.6 as a non-root user and `make test-package`
  pass on the released source.
- Not verified: a real WordPress installation, live hosting, the DDEV runtime, the native updater,
  or a signed release.

## Release status: owner-approved without integration qualification

Published at the owner's direction on 2026-11-01, like 0.9.0 and 0.9.1, **without** live hosting,
DDEV or updater qualification. The receipt pins the runtime files and the ZIP.

- **Unsigned.** No update signing key has been provisioned, so `GitHubUpdater::PUBLIC_KEY` is empty
  and this release's `update.json` carries no signature unless the repository has the
  `ZOER_CONNECT_UPDATE_SIGNING_KEY` secret. Updating from 0.9.1 works as before (SHA-256 from the
  same release); administrators who can update plugins see a notice that updates are unsigned.
  A later release that ships a public key makes every following update require a signature.
- **Existing pairings keep working.** Keys stored before 0.10.0 that have Push keep code access
  (flagged as legacy keys). A key created or reset after the update needs **Code** ticked before
  Zoer can push plugins or themes to that site; without it the import is refused when it is created.
