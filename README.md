# Zoer Connect

Zoer Connect transfers selected WordPress resources through HTTPS with verified recovery. **The current source is the 0.5.4 development version**: the request-protection MU file no longer breaks copies of a site or plugin removal ([notes](releases/0.5.4.md)). **0.5.3** (published without live qualification) added capability-negotiated compact import acknowledgements, subdirectory original URLs and no orphan source roles option ([notes](releases/0.5.3.md)). **Version 0.5.2 (API version 2) migrates updates to this public repository**, with [native WordPress updater qualification](releases/0.5.2.md). Transfer behavior is unchanged from qualified 0.5.1, including a completed Hostinger Intramurals Pull and DDEV local copy in [the release notes](releases/0.5.1.md). It fixes empty-file seals, bounded small-file preparation, portable hidden metadata and mixed-file download boundaries; the existing 0.5.0 Push/recovery qualification remains in [its release notes](releases/0.5.0.md). It moves toward WP Migrate DB Pro parity: filtered database Pull (tables, post types, revisions, spam, transients), theme/plugin selection modes and a media date filter, a read-only diagnostics preflight, opt-in import options (custom and variant replacements, path replacement, review before activation, late fencing, schema-validated table creation, author matching, activation-setting control, pause/resume, backup cleanup, destination-only find-and-replace, cache purging, safe errors) and batched Push uploads that pack many 256 KiB blocks into one request. Every new option is optional; clients that omit them get 0.3.14 behaviour. Earlier releases added resumable 2 GiB block publication (0.3.5), shared-hosting replacement and serialized-state preservation (0.3.4), and automatic Push setup on key generation (0.3.14). SparkLab was migrated with 0.3.x from its managed local source to `https://sparklab.unbc.ca/`; qualification evidence is recorded in the parent repository’s `output/ui-audit/`. WP Migrate was used as a workflow reference; this implementation is independent.

See the [operating guide and implementation lessons](https://github.com/ahzs645/zoer/blob/main/docs/zoer-connect-operations.md) for first-site setup, recovery, WP Migrate comparisons and remaining work.

## Transfer workflow

The Zoer connection dialog supports remote Pull with pause/resume/cancel, and Push from a managed local DDEV source or from a verified Pull of another connected site. The local source exports its database in a background CLI worker on the existing DDEV server, using one InnoDB consistent snapshot. It does not depend on a hosting HTTP request staying open. Verified, immutable artifacts are downloaded to private Zoer storage and uploaded in authenticated 256 KiB blocks, one block per `/chunks` request or many per `/batch` request.

The destination imports through `/wp-json/zoer-connect/v1/imports`. Each request advances a durable private journal. SQL is parsed as data rather than executed. Destination tables are staged and verified before cutover. Selected files retain verified backups. A must-use bootstrap blocks ordinary WordPress requests during activation and serves authenticated recovery before regular plugins or themes execute. Finish reopens the site. Rollback checks every affected table and file before restoring anything; it tolerates regenerated transient caches and refuses substantive later edits.

Destination home/siteurl, administrator accounts, roles, connector identity, search-engine visibility and selected environment settings are retained. By default, source authors map to the destination connection's administrator (`authorMapping: "match"` maps by login, then email). Theme/plugin activation settings are preserved when their resources are not selected. After a database or plugin/theme file Push or rollback, the next normal WordPress request refreshes permalink rules without rewriting `.htaccess`. Every nonidentity source table must have a matching existing destination schema (or, with `createTables`, a strictly validated source schema); unsupported tables are rejected rather than silently omitted.

## Destination setup

1. From 0.3.14, generating a connection key enables **Push** and prepares **Shared-hosting migration** automatically. Pair that key with Zoer. Pull remains off until enabled. Older versions require enabling Push and shared-hosting migration manually.
2. Automatic setup installs site-level MU protection and binds readiness to this site and protection code. It does not pause WordPress or publish content. Existing permissions, revoked access and advanced setup are preserved, including on key reset. If private storage or hosting compatibility prevents setup, the key remains available with an administrator error message; resolve the reported issue and save Push permissions to retry. Existing incomplete setups retain the manual recovery controls.
3. In Zoer, test the connection, choose the source and resources, prepare an export, confirm the destination address and replacement, then import.
4. Finish to reopen the site; inspect pages and administrator access. Use the same connection to recover interruptions. Rollback retains conflict checks and refuses detected later edits.

This is replacement, not a concurrent-edit merge. Earlier requests and external writers are not guaranteed to stop; avoid editing during migration. Requests reaching the site's MU protection pause during application/recovery. Original tables are retained by table renames and selected files have backups. Detected content changes can stop activation or prevent rollback. Coherent private journal storage and working filesystem/database locks remain necessary; distributed multi-host coordination is not provided.

Advanced verified-worker setup remains available for isolated environments that can prove all PHP workers adopted the fence. It retains Linux `/proc` inventory checks and writer declarations. Shared-hosting mode never records those declarations as established facts.

Changing fence code invalidates new-import readiness. Existing recovery remains available. Do not delete the connector, earliest MU bootstrap or private journals while a transfer is active. 0.5.0 changes the sealed fence runtime: repeat native request-protection setup before new source-pause exports or imports. Active transfers keep authenticated recovery; never update during an active transfer.

## Supported boundary

- Single-site WordPress 6.5+, PHP 8.1+, private writable storage outside every public document root.
- Existing matching InnoDB tables with primary keys (or, with `createTables`, tables created from a validated source schema); foreign keys and triggers are rejected. Identity tables remain at the destination. Staged table names are limited to 48 characters.
- Local exports: configurable quota (16 GiB by default, 1 MiB–64 GiB), 4 GiB per artifact, repeated 64 MiB free-space reserve checks, 30-minute worker deadline, immutable block checksums and restart/cancel handling. A failed worker starts a fresh transaction rather than appending an incomplete snapshot.
- Destination SQL: at most 4 GiB; row batches at most 4 MiB. With an updated block-capable Zoer backend, individual selected files and existing destination originals support up to 4 GiB. Upload, verification, backup and restoration process 256 KiB blocks with durable progress. Older clients/jobs retain the legacy 32 MiB path. The configured incoming transfer quota and independent backup/restore free-space checks still apply. New import manifests are bounded to 8 MiB; other JSON import requests remain 2 MiB.
- Upload requests: `/chunks` carries one 256 KiB block in at most 2 MiB of JSON; `/batch` carries up to 1,024 spans and by default at most 8 MiB (less when `post_max_size` is smaller), with about 2 seconds of server work per request.
- Importable files: selected themes, plugins and media. Core, wp-config, MU plugins, connector files, executable uploads, symlinks and unsafe paths are excluded.
- Advanced verified-worker setup requires readable Linux `/proc` process information and standard, single-threaded PHP-FPM, CGI or LSAPI workers. It checks every PHP process under the same operating-system account; a long-running CLI job or another site’s idle worker may delay readiness until it exits or adopts protection. Renamed/custom PHP interpreters, embedded or multithreaded runtimes, hidden process inventories and forked/unfenced background writers are unsupported. This is a compatibility check, not a guarantee for every shared host.
- Shared-hosting mode in 0.3.9 permits regular `advanced-cache.php` and `object-cache.php` drop-ins. They execute before MU protection and can serve stale pages; exclude connector API routes from page caches and purge page/CDN caches after migration (`purgeCaches` calls known cache plugins but cannot purge a host or CDN cache). Database, sunrise and maintenance drop-ins, symlinked drop-ins and nonstandard content locations remain unsupported. Advanced verified-worker mode still rejects all early drop-ins. External SQL writers are outside the protection guarantee.
- Hosted read-only Pull retains a consistent single-request database snapshot (256 MiB / up to 40 seconds). Optional source-pause export prepares larger snapshots across requests with typed keyset table/row checkpoints and checksummed SQL parts. It requires native key Push and Pull, request-protection readiness, InnoDB primary keys, MariaDB 10.1.1+ or MySQL 5.7.8+, and explicit confirmation that earlier requests and external/background writers stopped. HTTP paging cannot preserve one transaction across requests. SQL reads use a one-second database execution budget and two-second metadata lock waits; database interrupt checks are cooperative, so this is not a hard wall-clock deadline. Each part targets 4 MiB/about three seconds and permits a single SQL statement up to 16 MiB. Cancel or successful database sealing releases the source pause; idle expiry is one hour with a 24-hour maximum lifetime. Expired snapshots must start fresh.
- Revoking/rotating a key invalidates its generation. Existing jobs cannot be rebound automatically to a new key. Keep the original authorized connection available for recovery. A WordPress administrator can still clean up finished imports of an earlier key from Tools → Zoer Connect.
- Replacements: at most 50 custom rules and 250 rules in total; find/replace text up to 4,096 bytes, regex patterns up to 500 bytes. The per-value limit is 16 MiB (input and output) and applies only to values a rule can match; unrelated larger values pass unchanged (0.3.x: 1 MiB for every value). Literal replacements preserve unrelated serialized bytes without deserialization. Serialized objects or references requiring changes remain unsupported and are refused.
- Matching terminal uploads can supply cached files under the same destination/key generation. Reused files are hashed before activation; database chunks are uploaded again. Cleaned-up imports cannot be reused.
- Private backup journals are retained until cleanup. This is replacement, not merging concurrent edits or preserving arbitrary source user identities.

## Authentication and API

Connection keys contain 256 random bits, are shown once, and are stored only as hashes in WordPress. Zoer stores its copy encrypted as a host-only secret. Requests use `X-Zoer-Connection`, never URL credentials. HTTPS, current administrator ownership and per-direction permission are checked. Public import/recovery uses native connector keys; application passwords remain supported for legacy staging endpoints.

- `/status`: canonical destination, version, `apiVersion`, readiness, permissions, capabilities, `batchTransports` and `batchLimits`.
- `/diagnostics`: read-only preflight inventory and warnings (Push or Pull permission).
- `/exports`, `/exports/paged`: remote export create/status/step/chunks (or manifest/batch)/cancel.
- `/imports`: idempotent create and list; `/{id}` status (`?view=upload` for the upload cursor); `/{id}/chunks`, `/batch`, `/step`, `/finish`, `/rollback`, `/pause`, `/resume`, `/approve`, `/cleanup`.
- `/jobs`: legacy private file staging. Its old `/publish` route remains unimplemented; imports use the dedicated protocol.

Import requests are bounded to 2 MiB JSON (`/batch` octet-stream and multipart bodies are streamed and bounded by the batch limits); decoded upload blocks are 256 KiB. Job state, source/destination binding, sequence IDs and checksums determine retries. Clients never supply executable SQL or destination filesystem paths; `sourcePath` is only replacement text.

### Compact import acknowledgements (0.5.3)

0.5.3 adds optional `capabilities.compactImportResponses`. Clients must negotiate this capability before requesting `?view=compact` on native import creation, status, steps or controls (including finish, rollback, pause, resume, approval and cleanup). Omitting the query preserves the detailed API; `?view=upload` remains the authoritative upload cursor. The view is outside the create body, so selecting it does not change the immutable import binding or recovery policy.

A compact response carries `responseView: "compact"`, `detailsAvailable: true`, exact `id`, `target`, `sourceUrl` and `migrationMode`, plus phase, fence, cursor, timestamps, artifact count, recovery refusal and safe error. `stats` provides numeric replacement/table/row counts, author totals, at most three bounded replacement excerpts, `sampleCount` and `samplesTruncated`; complete artifacts, offsets, per-table statistics, options and all samples remain available through ordinary detailed status. While uploading, snapshotting, reusing artifacts or cancelled, `progress.uploadedBytes` is `null` and `uploadProgressAvailable` is false; clients use the upload view instead of treating omitted offsets as complete. Compact requests refuse source or destination identities over 2,048 bytes before advancing a job; the detailed API retains those identities unchanged.

This reduces repeated response bytes and per-artifact filesystem checks. It preserves the existing complete crash-safe journal, including its decoding, hashing and persistence costs. It does not introduce a faster publication scheduler or change verification, backups, fences or rollback. Temporary-file tests cover native capability/query selection, 100,000 artifacts, legacy detail, finish replay and guarded rollback; this addition is not yet a released or hosting-qualified feature.

### Subdirectory sources and table prefixes (0.5.3)

Export `source` adds `originalUrls`: the source `siteurl` when it differs from `home` (WordPress in a subdirectory or on another address), otherwise `[]`. Clients forward it as the import's `originalUrls`, which imports already accept, so URLs under the siteurl are replaced as well as the home URL. An unusable siteurl (not an http(s) URL, or 2,048 bytes or longer) is left out.

When the source table prefix differs from the destination's, an import no longer stages the source's `{sourcePrefix}user_roles` option. Users are never imported and the destination keeps its own `{prefix}user_roles`, so the source row was only an orphan option.

## API version 2 (0.4.0)

All additions are optional. A client that sends none of them gets 0.3.14 behaviour, including identical idempotent export bindings, the 0.3.14 replacement rules and the early fence. Clients must check `capabilities` before sending an option. Everything below is exercised by the unit suites and `tests/e2e-docker/`; none of it is qualified on real hosting yet.

### Status

`GET /status` adds `apiVersion: 2`, `version: "0.4.0"` and capability flags `replacementRules`, `replacementVariants`, `reviewPause`, `createTables`, `authorMapping`, `keepActivePlugins`, `lateFence`, `importPauseResume`, `importCleanup`, `importList`, `siteReplace`, `cachePurge`, `databaseFilters`, `resourceModes`, `mediaSince`, `diagnostics` and `safeErrors` (all `true`), plus `batchUpload: true` and `batchDeflate` (true when PHP's zlib `inflate_init` and `inflate_add` are both available). `batchTransports` lists `octet-stream`, `multipart` (only when PHP `file_uploads` is on) and `json`; `batchLimits` gives the octet-stream limits (see [Batched upload](#batched-upload)).

### Diagnostics

`GET /diagnostics` (connection key with Push or Pull permission) returns `wordpress` (version, prefix, home, siteurl, abspath, contentDir, uploadsDir, locale, permalinkStructure, blogPublic), `php` (version, memoryLimit, maxExecutionTime, postMaxSize, uploadMaxFilesize, zip/openssl/curl/mysqli), `database` (server `mysql`/`mariadb`, version, charset, collate, lowerCaseTableNames, up to 2,000 tables with suffix, prefixed, engine, rows, bytes, primaryKey, foreignKeys, triggers), `postTypes` with counts, `themes` (with active and parent), `plugins` (slug, file, active), `muPlugins`, `dropins`, `warnings` and `pluginUpdate` (`current`, and `latest` from WordPress's cached update check). Warning codes: `firewall_plugin` (Wordfence, Defender, Solid Security, All-In-One WP Security, Sucuri, NinjaFirewall or a firewall `auto_prepend_file`), `page_cache_plugin` (Breeze, WP Rocket, W3 Total Cache, WP Super Cache, LiteSpeed Cache, WP Fastest Cache, Cache Enabler, SG Optimizer, Autoptimize, or an `advanced-cache.php` drop-in), `object_cache_dropin`, `mixed_case_tables`, `non_innodb`, `foreign_keys`, `triggers`, `blog_private`, `no_https`. Nothing is changed. Paths are returned to authenticated clients only.

### Pull filters and profile modes

`POST /exports` and `/exports/paged` accept `database: true | false | {tables?, postTypes?, excludeRevisions?, excludeSpam?, excludeTransients?}`. `true` keeps the 0.3.14 query byte for byte.

- `tables` lists up to 500 suffixes after the prefix; only selected tables are read, so an unselected non-InnoDB table no longer blocks a Pull, and an unknown suffix is refused.
- `postTypes` is an inclusion list (revisions are post type `revision`); `excludeRevisions` drops revisions. Postmeta, comments, commentmeta and term relationships are dropped only when their parent post (or comment) was excluded; link-category relationships and orphaned rows are kept.
- `excludeSpam` drops `comment_approved='spam'` and its meta. `excludeTransients` defaults to true (the 0.3.14 behaviour); with a filter object the LIKE patterns escape `_`, so only real transient rows are skipped.
- Filters are WHERE clauses inside the same consistent snapshot. Connector options, `wpmdb*` options, application passwords and sessions remain excluded from Pull. The snapshot's schema check ignores `AUTO_INCREMENT`, so a concurrent insert (a transient, a cron lock) no longer fails it with "Schema changed during export."
- `profile` accepts `themesMode`/`pluginsMode` (`all`, `active`, `selected`, `except`), `themesItems`/`pluginsItems` (directory names, or a single-file plugin name such as `hello.php`) and `mediaSince` (`YYYY-MM-DD`: uploads modified on or after that UTC midnight). `active` includes the active theme and its parent. Absent or `all` values normalize to the 0.3.14 profile.
- The response `source` adds `abspath` (untrailingslashed) and `tables` (exported suffixes).

### Import options

`POST /imports` accepts an optional `sourcePath` (absolute source ABSPATH, at least two characters, no control characters) and an optional `options` object. Unknown keys are refused. Every key is optional:

| Option | Absent (protocol default) | Zoer UI default | Capability | Effect |
| --- | --- | --- | --- | --- |
| `replacements.automatic` | `true` | `true` | `replacementRules` to turn off | Source home and original URLs → destination URLs. |
| `replacements.variants` | `false` | `true` | `replacementVariants` | http/https twins, JSON-escaped (`https:\/\/`), rawurlencoded and protocol-relative (`//host`) forms. |
| `replacements.paths` | `false` | `true` | `replacementRules` | `sourcePath` → destination ABSPATH (and its JSON-escaped form), only when the source path has at least two segments and only up to a path boundary. |
| `replacements.custom` | `[]` | `[]` | `replacementRules` | Up to 50 `{find, replace, regex?, caseSensitive?}` rows, applied in order after the automatic rules. Regex rows need delimiters; `caseSensitive: false` adds the `i` modifier (regex) or matches literals case-insensitively. |
| `replaceGuids` | `true` | `true` | `replacementRules` to turn off | `false` leaves `posts.guid` unchanged. |
| `keepActivePlugins` | `null` | `null` | `keepActivePlugins` | `null`: keep the destination's `active_plugins` unless plugins are selected (0.3.14 inference); `true`: always keep; `false`: take the source's. |
| `keepActiveTheme` | `null` | `null` | `keepActivePlugins` | Same for `template`/`stylesheet`. |
| `authorMapping` | `administrator` | `match` | `authorMapping` | `match` adds the `mapping_authors` phase: source users are matched by `user_login`, then `user_email`; unmatched posts go to the connection administrator and unmatched comments are unlinked (`user_id` 0). |
| `createTables` | `false` | `false` | `createTables` | Missing destination tables are created, and mismatched schemas replaced (the old table kept as backup), from a strictly validated source schema. |
| `partialDatabase` | `false` | set by Zoer for table-subset Pulls | `databaseFilters` or `createTables` | Skips the check that the snapshot contains the nine core content/settings tables. |
| `fence` | `early` (`activation` for `kind: "replace"`) | `activation` | `lateFence` | `activation` stages tables while the site stays live and pauses it only for file application and table swaps. |
| `review` | `false` | `false` | `reviewPause` | Stops at `review_required` until `/approve`. Requires `fence: "activation"`; refused otherwise. |
| `purgeCaches` | `false` | `true` | `cachePurge` | After finish or rollback, the next normal `wp_loaded` calls known page-cache purge hooks. |

**Absent `options` = 0.3.14 behaviour.** When the create body has no `options` key at all, the import records `legacyReplacements` and applies the 0.3.14 rules byte for byte: every original URL, untrailingslashed, is replaced by the destination home, one literal rule after another in the given order (an earlier rule's output can be matched by a later one). With any `options` object (even `{}`), generated URL, variant and path rules run as one longest-match-first pass, so a destination URL that contains the source URL is never rewritten twice; original URLs beneath the source home (for example a WordPress subdirectory siteurl) map to the destination siteurl, and all others to the destination home. Generated rules match literally and case-sensitively; custom rows follow. Replacement counts per table and up to 20 before/after samples (240 characters around the first difference) are recorded.

Summaries of every `/imports*` response add `kind`, normalized `options`, `fence`, `resumePhase`, `stats` (`replacements`, per-table `rows`/`replacements`/`created`/`schemaReplaced`, `samples`), `progress` (`uploadedBytes`, `totalBytes`, `tableIndex`, `tableCount`, `rowsRead`), `authors` (`matched`, `fallback`), `error`, `cleanedUp`, `updatedAt` and `finishedAt`.

### Phases

Early fence (default and 0.3.14; the site is paused from `reserving` on):

`uploading → checking_artifacts → scanning_database → [mapping_authors] → reserving → preparing_tables → reading_database → verifying_tables → preparing_files → applying_files → activating_tables → verification_required → complete`

Activation fence (the site stays live until the fenced check in `reserving`):

`uploading → checking_artifacts → scanning_database → [mapping_authors] → preparing_tables → reading_database → verifying_tables → [review_required] → reserving → preparing_files → applying_files → activating_tables → verification_required → complete`

In `reserving`, the activation fence first compares every live table with its staging fingerprint without pausing the site, then reserves the fence and checks again from scratch before any file changes. A live change detected at either point ends the import `cancelled` with a safe error, releases any fence and leaves the site live; nothing live was replaced. Live cron and maintenance options are re-copied into the options stage under the fence just before the swap. Imports without a database go from `checking_artifacts` to `reserving` (or `review_required`). `reusing_artifacts` precedes `uploading` when `reuseImportId` is set. `/finish` moves `verification_required` through `finishing` to `complete`.

Rollback before anything live changed (every phase before the fence; with the activation fence also `preparing_tables` through `review_required`, and `reserving` before its first check) simply ends the import `cancelled`; staged private tables remain until cleanup. Later rollbacks run `rollback_reset → rollback_reset_files → rollback_preflight_tables → rollback_preflight_files → rollback_tables → rollback_files → rolled_back`, refusing (with `rollbackRefused`, and the site reopened) when a preflight detects later edits.

### Review, pause and cleanup

- **Review.** At `review_required` the summary carries replacement stats, samples and author counts while the site is still live. `POST /imports/{id}/approve` moves it to `reserving`; repeating an approval after a lost response is a no-op. Rollback at this point discards the staged work (`cancelled`).
- **Pause/resume.** `POST /pause` stores the current phase as `resumePhase` and sets `paused`; `POST /resume` restores it. Terminal phases, `finishing` and rollback phases cannot pause. Pausing does not release a fence that is already reserved: with the early fence, the site stays paused until the import is resumed and finished or rolled back.
- **Cleanup.** `POST /imports/{id}/cleanup` accepts only `complete`, `rolled_back` or `cancelled` imports. It drops that import's `zoer_b_`, `zoer_s_` and `zoer_l_` tables in bounded (about 2 s) batches, reporting `cleanedUp: false` until the last one, then deletes artifact data, author maps, upload indexes and file backups. `state.json` remains with `cleanedUp: true`; rollback and upload reuse are refused afterwards. Cleanup is refused while another import is reusing the uploads.
- **Administrator cleanup.** Tools → Zoer Connect → **Transfers** lists the newest 50 imports from private storage and offers **Clean up backups** for finished ones (administrator, nonce and confirmation required). It works on journals of any key generation, so backups from before a key rotation can still be removed; it remains bound to this destination and to terminal imports. The same page has editable export profiles with the theme/plugin modes and media date.
- **List.** `GET /imports` returns `{imports: [...]}`, newest first, at most 50, for the current key generation and destination. Entries are light summaries (`artifactCount` instead of per-artifact arrays) and are read without the import lock.

### Destination find-and-replace (`kind: "replace"`)

`POST /imports` with `kind: "replace"`, `target`, the migration-mode confirmation and `options: {replacements: {custom: [...]}, tables?, review?, fence?, replaceGuids?, purgeCaches?}` runs custom rules against this site's own database. At least one custom row is required; transfer fields (`database`, `files`, `sourceUrl`, `sourcePrefix`, `sourcePath`, `originalUrls`, `resources`, `reuseImportId`) are refused. `tables` lists up to 500 suffixes; the default is every prefixed table except `users` and `usermeta`, which can never be selected. The job starts in `snapshotting`: it stages and fingerprints each selected live table first, then writes a bounded snapshot of only those tables with `DatabaseExporter` (transients excluded; other tools' options such as `wpmdb*` settings are kept, unlike Pull), so any write after the fingerprint cancels activation instead of being overwritten. It then follows the normal pipeline with automatic rules, author/comment rewriting and table creation off and `partialDatabase` implied. `fence` defaults to `activation`; Zoer always sends `review: true`.

### Table creation and other installations

A source `CREATE TABLE` is used only when it is a single statement of at most 64 KiB that starts with ``CREATE TABLE `<source name>` (``, has exactly one column list closed by `ENGINE=InnoDB` and known table options, and has a `PRIMARY KEY`. It must not contain `;`, any backslash, comments (`--`, `/*`, `#`), control characters other than newlines, an `@`, or (outside quoted identifiers and strings) `FOREIGN KEY`, `REFERENCES`, `DATA DIRECTORY`, `INDEX DIRECTORY`, `CONNECTION`, `UNION`, `PARTITION`, `SELECT`, `LOAD_FILE`, `SLEEP`, `BENCHMARK`, `TABLESPACE`, `ENCRYPTION`, generated/virtual/stored columns, `INSERT_METHOD`, `TEMPORARY`, `AS (` or `DEFAULT (`. The table name is rewritten to the private stage name before execution. Created tables roll back by renaming them to a `zoer_s_` name, which cleanup drops.

`createTables` and replace jobs refuse tables that belong to another WordPress installation sharing the database: a longer prefix that starts with this site's prefix and has its own `options` and `posts` tables (for example `wp_blog2_` beside `wp_`).

### Safe errors and cache purge

Import failures return `{code: "zoer_import_failed", message, phase}` (HTTP 400 for invalid input, 409 otherwise). The message is shown only when the plugin authored it (its own exception classes, or exactly `RuntimeException`/`InvalidArgumentException`); anything else becomes "Import could not advance. Retry or roll back using the same connection." Filesystem paths are replaced by `[path]` and the text is capped at 300 characters. The same object is stored as the import's `error` until the next successful step. Authentication and routing failures keep their `zoer_import_unavailable` responses.

`purgeCaches` queues the `zoer_connect_cache_purge_pending` option when the import finishes or rolls back. On the next normal `wp_loaded` the marker is deleted first, then LiteSpeed, WP Rocket, W3 Total Cache, WP Super Cache, Breeze, WP Fastest Cache, Cache Enabler, SG Optimizer and Autoptimize purge hooks and `wp_cache_flush()` are called, each isolated so a failing cache plugin cannot break the request or keep the site fenced.

### Batched upload

`POST /imports/{id}/batch` uploads many 256 KiB blocks in one request. It is early-dispatched like every other import action, with identical key, Push permission and administrator-owner checks, and accepts uploads only in phase `uploading`. A batch is an ordered list of spans `[artifactIndex, offset, length]`: `offset` is block-aligned, `length` is a multiple of 256 KiB unless the span ends the artifact, and one request may carry many small files and several blocks of one file.

Transports (the client picks one per request):

1. **`application/octet-stream`** (preferred): the body is `"ZBT1"`, a big-endian uint32 header length `H` (2–65,536), `H` bytes of JSON header `{"v":1,"spans":[[i,o,len],…],"payloadBytes":N,"enc":null}`, then the span bytes concatenated. `Content-Length` is required and must equal `8 + H + payloadBytes`. With `"enc":"deflate"` each span is `[i,o,rawLen,encLen]` and its bytes are a separate zlib stream (RFC 1950, not raw deflate): inflation stops at `rawLen`, and the stream must end exactly at `encLen` with exactly `rawLen` bytes, otherwise the span is rejected as `decode`. The body is read from `php://input` in pieces of at most 256 KiB (4 KiB for deflate input) and never buffered whole.
2. **`multipart/form-data`**: a file part named `batch` carrying the same framed bytes, read from the uploaded temporary file. Advertised only when PHP `file_uploads` is on.
3. **JSON**: `{"v":1,"spans":[[i,o,len,"<base64>"],…]}`, or with `"enc":"deflate"` `[i,o,rawLen,encLen,"<base64 zlib>"]`, within the 2 MiB JSON limit.

Per block, the SHA-256 is verified against the manifest's `chunkSha256` before anything is written (`digest_mismatch`). Then a block already inside the staged bytes is skipped when identical (idempotent retry) and rewritten when it differs; a block that overlaps the end is written at its offset (repairing a torn tail); a block beyond the end is refused as `gap`. Spans are processed in order and the request stops at the first rejected span (blocks before it stay applied) or between blocks once about 2 seconds have passed since the request started (`deadlineHit`; at least one block is always attempted). Artifacts without per-block digests (legacy whole-file manifests) are refused as `unverifiable`; clients upload those through `/chunks`. Out-of-range spans are `bounds`. Only `import-<id>/artifact-N/data` is written.

Response (small; no artifact list): `{"v":1,"phase":"uploading","acceptedSpans","appendedBytes","cursor":{"index","offset"},"uploadedBytes","totalBytes","complete","deadlineHit","serverMs","rejected":null|{"span","code","expectedOffset"},"limits":{…}}`. `expectedOffset` is the block-aligned staged size of the rejected span's artifact.

Limits: `blockBytes` 262,144; `maxBatchBytes` = min(`post_max_size` − 64 KiB, 8 MiB), and for multipart also at most `upload_max_filesize` − 64 KiB − 8 bytes (with `post_max_size = 0` the PHP ceiling is 64 MiB); the `zoer_connect_max_batch_bytes` filter (`$max`, `$transport`) may lower or raise it within those PHP ceilings and 64 MiB, never below one block; `maxJsonBatchBytes` 2,097,152; `maxSpans` 1,024; `deadlineMs` 2,000. A body over these limits, or one PHP discarded because of `post_max_size`/`upload_max_filesize`, is answered with HTTP 413 `{"code":"zoer_import_body_limit","message","limits"}` carrying the limits for that transport, so a client can resize without guessing. An unread octet-stream tail is drained (bounded) before answering, so proxies deliver the response instead of resetting the connection.

Upload state is kept outside the journal so a batch never decodes every block digest: at create the plugin writes `artifacts.idx` (per artifact: uint64 bytes, uint32 first block, uint32 verified flag), `blocks.idx` (32 raw SHA-256 bytes per block) and, last, `upload.json` (cursor and byte counts), each through a flushed temporary file and rename. Journals created by earlier versions get them built once, lazily, while still uploading. Batch requests read the phase and binding from the journal's leading keys. `GET /imports/{id}?view=upload` returns `{cursor, uploadedBytes, totalBytes, phase}` without the import lock; the cursor offset is block-aligned, so a torn tail is resent.

Compatibility: `/chunks` responses and error messages are unchanged and share the same block writer, so a job may switch between `/chunks` and `/batch` mid-upload. The size check at `uploading → checking_artifacts` and the rehash in `checking_artifacts` remain the authority. Clients that do not see `capabilities.batchUpload` keep using `/chunks`.

Stable releases also include an `update.json` asset generated only from the exact qualified ZIP. WordPress 0.5.2 and later read `https://github.com/ahzs645/zoer-connect/releases/latest/download/update.json` and use the matching versioned GitHub Release ZIP and metadata; prereleases contain no update metadata. The `v0.5.2` release alone also publishes the final compatibility bridge into `ahzs645/zoer-connect-releases` using its existing scoped deploy key. Future releases need no separate feed checkout or deploy key. Checks must pass before any release assets publish. If the final legacy-feed step fails after the GitHub Release publishes, retry the same immutable tag run; it compares existing assets before completing the bridge. Do not declare the bridge complete until both endpoints match. Do not move an already published release tag or change a published version's ZIP.

Install the current stable ZIP once through WordPress's Upload Plugin screen. Connectors older than 0.5.2 check the legacy public `latest.json` feed during ordinary WordPress plugin update checks. ## Paged exports (0.3.7)

Updated Zoer clients can negotiate pagedExport and use exports/paged. Traversal and immutable file preparation checkpoint after at most 250 entries or four seconds per request (one file copy/hash can extend that soft budget). Manifests return 500 entries per page. Downloads pack up to 32 chunks and 1 MiB into one response. Limits are 100,000 files, 4 GiB total, 32 MiB per source file and a separate database snapshot bounded to 256 MiB/40 seconds. Active requests renew the one-hour idle expiry within a 24-hour maximum lifetime. Earlier clients keep their existing export flow and limits. No full-site external clone is claimed by protocol qualification alone.

Exclude the connector REST namespace from any full-page hosting cache. Aram's Breeze cache required an explicit Never Cache URL entry even though connector responses set no-store. Confirm unauthenticated status returns 401 and a connection test reflects current plugin version and storage readiness.

## Large-transfer protocol (0.5.0)

Negotiate `capabilities.blockDigestExport` and submit `largeTransfer: true` on `/exports/paged`. Individual artifacts are bounded to 4 GiB, the configured transfer quota defaults to 16 GiB, manifests have at most 100,000 entries, and downloads carry at most 4 MiB/32 chunks. The optional database mode adds `snapshotMode: "maintenance"` and `sourceQuiescenceAccepted: true`. `/step` reports `sourcePaused` and table/row/byte checkpoints. Preparation copies and then verifies source files in bounded requests before advertising them.

Large manifests bind exact paths/sizes and `digestFormat: "sha256-blocks-v1"`: `sha256` is SHA-256 over the ordered raw SHA-256 digests of 256 KiB blocks, including the final short block. Zoer verifies every chunk and the finished block root, then computes a conventional whole-file SHA-256 before importing, publishing or downloading a backup. SQL parts also retain their own byte ranges, SHA-256 and typed row cursor. No PHP hash context is serialized. Lost responses replay from committed offsets and truncate uncommitted tails; missing committed bytes fail closed.

Hosted quotas are configured in Tools → Zoer Connect, or by `ZOER_CONNECT_TRANSFER_QUOTA_BYTES` in wp-config.php (which overrides the option). Zoer's backend and DDEV bridge use `ZOER_WORDPRESS_TRANSFER_QUOTA_BYTES`; configure both processes consistently. These are per-transfer incoming-byte quotas, not a shared account-wide reservation: simultaneous transfers and backup originals can require additional space, so checks repeat before allocations and restoration. Quota settings are preserved when importing another site's options. The separate Updraft browser-upload workflow retains its existing 1 GiB/component and 2 GiB/set bounds. Native file-profile downloads and clients that omit `largeTransfer` retain their legacy bounds.

The query budgets follow [MariaDB SET STATEMENT](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/set-commands/set-statement) and [MySQL MAX_EXECUTION_TIME](https://dev.mysql.com/doc/refman/8.0/en/optimizer-hints.html). MariaDB documents cooperative interrupt checkpoints rather than a strict request deadline.
